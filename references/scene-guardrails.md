# 场景护栏：改动范围与场景默认值

> 定位：本文档回答「这次编辑能动多少、哪些地方默认不动」。核心顺序：**用户要求优先 > 文体要求 > 模式命中**。31 条模式分类法只是检查线索，永远不能覆盖用户的改动范围与文体要求。

## 一、改动范围四档（用户优先）

| 档位 | 定义 | 允许 | 不允许 / 示例 |
|---|---|---|---|
| **structural**（自由调整） | 可删、并、重排，保留有效信息和作者意图 | 删句、并句、重排段落、调整结构 | 不能丢信息、不能改判断强度。例：前「本次完成了对重试策略的调整。重试策略已经调整过了。重复请求从 24 次降到 7 次。」后「本次调整了重试策略，重复请求从 24 次降到 7 次。」 |
| **bounded**（保留结构） | 句内清理；整句删除只提建议，正文保留；不并句、不重排 | 句内压缩、替换、合并重复分句 | 不能整句删除进正文、不能并句、不能重排。例：前「接下来让我们深入看看缓存的作用。缓存可以复用已经取得的结果。」→ 只给建议「建议删除第一句」，正文保留原两句。 |
| **in-place**（只在原位改） | 不删句、不并句、不重排；要求保句数时也不拆句 | 句内逐处替换、压缩 | 不能改变句数与句子边界。例：前「这次更新彰显了团队对创新的追求。」后（原位）「这次更新新增导出、搜索和批量重命名。」 |
| **只标问题**（审稿模式） | 不改写，只指出问题与建议；不替作者撤回判断 | 列缺陷清单，每条引原文短语 | 不能落笔修改。例：前「本工具稳定可靠、快速响应、易于维护。」→ 标注「三个四字词并列较空泛，可考虑改为『运行稳定、响应快、方便维护』；是否修改由作者决定。」 |

用户指定档位时以用户为准；未指定时按场景默认值（见第二节）。

### minimal / standard / aggressive 三档说明

| 档位 | 含义 | 边界 |
|---|---|---|
| minimal | 只修最明显的语病和妨碍理解的冗余 | 任何档位都不放宽保真要求：数字、条件、承诺、归因、作者意图一律保留 |
| standard | 默认档：清理套话、重复铺垫、生硬句式 | 保留背景、定位、程度与作者评价；心理、感受类陈述先保留 |
| aggressive | 更彻底地清理黑话与叠用比喻 | 可能改变作者判断强度或作者自己的术语，需逐处核对；已知缺口：长文清理偏少 |

三档是清理强度，不是范围档位的替代品；选择 aggressive 也不能绕过用户指定的 structural/bounded/in-place/只标问题。注：参考实现中三档尚无分开的规则，实际效果接近。

## 二、场景默认值（≥8 个场景）

每个场景给出：默认改法｜保留边界｜短例（前→后）。

### 1. README

- 默认改法：句内清理套话、起跑式铺垫与重复赞美，保留功能定位、特性列表、安装与使用步骤。
- 保留边界：命令、路径、链接目标、YAML、代码块、表格数据、版本号、标题层级与锚点不动；不补写 README 未提供的特性或数据。
- 短例：前「欢迎使用本工具！它是一款功能强大的效率增强神器，让我们深入看看它的核心特性。」后「本工具是一款效率工具。核心特性如下。」

### 2. Release Notes

- 默认改法：删宣传句与句尾拔高（「彰显了……」「标志着……」），保留功能项、计划、状态与日期；保留版本间的前后差异。
- 保留边界：不把「计划」改成「已发布」、不把「尚未完成测试」改成完成；真实的三项功能不删项凑项；变更记录保留「从 X 调整为 Y」的对比。
- 短例：前「这次更新彰显了团队对创新的追求。它新增导出、搜索和批量重命名。离线编辑计划在下一版推出，目前尚未完成测试。」后「这次更新新增导出、搜索和批量重命名。离线编辑计划在下一版推出，目前尚未完成测试。」

### 3. issue / 群聊回复

- 默认改法：先给结论/决定，再给必要推理；删对读者已知背景的重述（回复的读者已共享上下文，重讲背景只会埋没结论）。
- 保留边界：保留条件、限制与「我建议」「可能」等情态；不替对方做决定；诊断与完整论证属于后续文档，不属于回复。
- 短例：前「关于你问的报错，先说明一下背景。这个报错通常是因为配置文件缺失，我建议你先检查配置，然后重试。」后「报错多半是配置文件缺失。先检查配置再重试。」

### 4. 公众号 / 博客文章

- 默认改法：删空泛铺垫、假对比、句尾拔高、套话收尾与「在当今……的时代」式背景；保留事实、态度与作者声音。
- 保留边界：保留作者观点、犹豫、幽默与第一人称；不替作者添加亲身经历、情绪或结论；「可能」不改成「确定」。
- 短例：前「在当今快速发展的时代背景下，本文旨在深入探讨时间管理之道。总而言之，让我们共同期待一个更高效的未来。」后「本文讨论时间管理。」

### 5. 个人随笔

- 默认改法：只清理妨碍理解的冗余与病句；保留个性、情绪、犹豫、第一人称和私人细节。
- 保留边界：不把随笔改成通用口语；具体而独特的细节（真实地址、怪异的引用、年代梗与圈内梗）保留；用户要求增强个人风格时用表达方式实现，不编故事。
- 短例：前「今天下雨，心情有点烦。但想了想，还是决定出去走走。」后「今天下雨，心情有点烦，但还是决定出去走走。」（合并重复主语，保留情绪。）

### 6. 学术与商务文本

- 默认改法：精简赘语与生硬句式；保留正式程度、归因、限定与论证结构，不强行口语化。
- 保留边界：被动句、四字格、名词化表达可符合文体；术语、版本、引用与出处保留；「研究表明」无出处时保留归属与论断，必要时在正文外提示缺来源，不删「研究表明」把结论变成已核实事实。
- 短例：前「本研究旨在对现有数据进行全面分析，以期深入探讨其潜在影响。」后「本研究分析现有数据，探讨其潜在影响。」

### 7. 翻译（结构保真）

- 默认改法：只做语言转换与表达自然化；结构保真优先，覆盖风格偏好。
- 保留边界：不擅自增删内容；不合并或拆分段落；不把 Markdown 结构改写成散文化中文；标题、列表、表格、链接目标保留；代码、命令、路径、ID 原样。
- 短例：前（英文）「The tool supports CSV export. It is fast and reliable.」后「该工具支持 CSV 导出，速度快且可靠。」（句数、信息与顺序不变。）

### 8. 代码块与数据

- 默认改法：逐字保留；只有用户明确点名修改注释或说明文字时才编辑相应部分，且不改程序行为；代码围栏里的普通文案仍可按要求清理。
- 保留边界：代码块（含注释、文档字符串）、行内代码、命令、路径、URL、链接目标、显式 ID、YAML front matter、数据保持原样；JSON 字符串中的直引号按结构化数据保护，不随正文标点规则改动。
- 短例：前「运行 `npm install` 即可快速安装所有依赖。」后「运行 `npm install` 安装依赖。」（命令原样，只清理散文。）

### 9. 长文（≥1000 字）

- 默认改法：整体改动保守，只做句内清理与明显语病修复；约 1000 字以上的中文公开长文默认保留句段结构。
- 保留边界：保留段落与句子的整体结构，不改动作者判断强度与作者自己的术语；已知缺口：长文清理偏少是已知现象，若明确要求「彻底清理」，改动会更大但可能改变判断强度或术语，需逐处核对。
- 短例：前「首先，让我们从背景说起。背景是团队在过去两年里尝试了三种方案。」后「背景是团队在过去两年里尝试了三种方案。」（删起跑式铺垫，段落结构不动。）

## 三、模式命中不能覆盖用户范围与文体

1. **约束优先级**（模式命中排最后）：① 保留信息和确定程度 → ② 遵守用户的编辑范围和文体 → ③ 匹配作者声音 → ④ 处理具体表达问题。
2. **模式是检查线索，不是词语黑名单**：单个词、标点、三项列表、四字词不是修改理由；「弱单独」项单独出现可不改，多处同段出现才处理。
3. **文体要求优先于模式**：学术/商务文本的正式程度、被动句与四字格可以符合文体；随笔的个性与情绪不因模式命中而被磨平；翻译的结构保真覆盖风格偏好。
4. **交付约定**：默认交完整改写稿，不附命中清单与评分；不需要修改时返回原文；只标问题时只给建议，不落笔。
5. **文件模式默认**：只改散文正文；代码、数据、链接、命令、路径、YAML、标题与锚点默认不动，改标题或结构需先检查引用。
